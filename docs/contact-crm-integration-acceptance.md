# TitanCore contact form → CRM: integration acceptance specification (DRAFT)

Status: **NOT DEPLOYED / NOT APPROVED**. This document is a design and test plan, not evidence of an operating integration.

- Public site: Netlify project `titancoreholdings`; registered form `titancore-contact` had 12 submissions at inspection.
- Website source: `contact.html` submits via `method=POST` and `data-netlify=true`; no direct CRM call.
- Draft PR #73 removes obsolete phone/SMS opt-in, adds Netlify honeypot, and sets `action='/thank-you'`. Live deployment is separate from GitHub; do not assume merge deploys the site.
- TitanCore Supabase project `jgpvrblzyznyprtffirw`, table `public.leads`: RLS enabled; no policies; no direct grants to `anon` or `authenticated`; `service_role` has INSERT. `id` is BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY, so an INSERT may omit it.

## Proposed trusted delivery design

1. **Keep the browser unprivileged.** Public form submits to Netlify Forms only. Never embed Supabase secret/service-role keys, Netlify API tokens, or webhook authentication secrets in HTML or client JavaScript.
2. **Select and document one ingestion path before implementation:**
   - Preferred when Netlify form-submission notifications can authenticate strongly: verified webhook to a server-side intake endpoint. Confirm the *actual* notification payload and authentication mechanism in Netlify settings; do not assume a signature header exists.
   - Otherwise: server-side scheduled reconciliation that reads verified Netlify submissions via documented authenticated API, paginates, and records a durable cursor. Do not build an unauthenticated public POST endpoint that trusts an arbitrary submission ID or client-supplied form payload.
3. **Authenticate before parsing/storing PII.** Reject unauthorized requests with 401/403; require HTTPS; apply payload-size limits, rate limits, and safe logging (request IDs, not names, messages, email addresses, tokens).
4. **Validate and normalize fields.** Accept only the expected form name; trim and bound lengths; require valid email, name, and message; map `name → full_name`, `email → email`, `phone → phone`, `organization → company`, `inquiry-type → service`, `message → notes`; set a controlled `status` such as `new` after confirming allowed status semantics. Do not copy SMS consent into marketing permissions; consent is absent from draft form.
5. **Deduplicate reliably.** Persist Netlify submission ID as a unique external key in a *separate restricted ingestion receipt table* or another approved idempotency store. Do not assume `public.leads` has such a column. Process repeats safely and record failures for controlled retry.
6. **Write server-side only.** Use a secret credential accessible only in function runtime; retain RLS and existing grants. Do not add `anon` INSERT/SELECT policies or broad dashboard SELECT policies to make the integration pass.
7. **Dashboard authorization is a separate gate.** Establish the approved employee/manager/owner identity model and row/tenant scoping; test both allowed and denied access before showing lead PII. Never use user-editable JWT metadata for authorization.
8. **Operational safeguards.** Secret rotation, retention schedule, audit receipts, delivery-failure alerting, replay handling, and privacy/consent review must be specified before release.

## Required isolated acceptance tests

- Legitimate sample submission: Netlify receives it; ingestion stores one lead and one receipt; authorized employee sees correct fields.
- Replay of same Netlify submission: no duplicate lead.
- Invalid/missing authentication: no database write and no PII in logs.
- Malformed fields/oversized message: safe rejection; no partial records.
- Simulated network failure: retry eventually succeeds once; no data loss or duplicates.
- Unauthorized dashboard account: cannot read lead or ingestion receipt.
- Honeypot submission: rejected by Netlify; normal submission still reaches success page.
- Mobile form: input, keyboard, validation, thank-you redirect and menu all work.
- Audit source-to-destination counts and identifiers without publishing customer PII.
